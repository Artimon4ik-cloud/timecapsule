# ADR-0006. Вынос фоновых задач в AWS Lambda

## Статус

Принято.

## Дата

26.11.2026

## Контекст

До выполнения лабораторной работы №7 приложение TimeCapsule выполняло фоновые задачи непосредственно внутри веб-запросов.

При запечатывании капсулы PHP-приложение ожидало завершения создания уведомления. Искусственная задержка отправки письма увеличивала время ответа сервера.

Открытие капсул также выполнялось внутри PHP-приложения при обращении пользователя к сайту. Если никто не посещал сайт, капсулы не открывались вовремя.

Кроме того, при использовании нескольких серверов в Auto Scaling Group каждый сервер мог выполнять проверку капсул, создавая дополнительную нагрузку на базу данных.

Необходимо было выбрать способ выполнения фоновых задач независимо от веб-запросов.

## Рассмотренные варианты

### Вариант 1. Выполнение задач внутри веб-запроса

Данный подход использовался в предыдущих лабораторных работах.

**Преимущества:**

- Простая реализация.
- Не требуются дополнительные сервисы AWS.
- Вся логика находится внутри PHP-приложения.

**Недостатки:**

- Пользователь ожидает завершения фоновых операций.
- Увеличивается время ответа сервера.
- При отсутствии посетителей капсулы не открываются вовремя.
- Отсутствует отдельная очередь для повторной обработки сообщений.

### Вариант 2. Использование cron на EC2

Cron позволяет запускать определённые команды или скрипты по расписанию на сервере.

Например, можно запускать PHP-скрипт открытия капсул каждую минуту.

**Преимущества:**

- Фоновые задачи выполняются независимо от веб-запросов.
- Простая настройка расписания.
- Не требуется создавать Lambda-функции.

**Недостатки:**

- Сервер должен постоянно работать.
- При остановке сервера фоновые задачи перестают выполняться.
- При использовании Auto Scaling одна задача может одновременно запускаться на нескольких серверах.
- Необходимо самостоятельно реализовывать повторные попытки и обработку ошибок.
- Требуется дополнительное обслуживание серверов.

### Вариант 3. Использование AWS Lambda, Amazon SNS и Amazon SQS

Фоновые задачи передаются отдельным сервисам AWS.

При запечатывании капсулы приложение публикует событие в Amazon SNS. Затем сообщение поступает в Amazon SQS, откуда его получает Lambda Mailer.

Для автоматического открытия капсул используется Lambda Opener, которая запускается каждую минуту через EventBridge Scheduler.

**Преимущества:**

- Пользователь не ожидает завершения фоновых задач.
- Сообщения хранятся в очереди до обработки.
- Поддерживаются автоматические повторные попытки.
- Необработанные сообщения перемещаются в DLQ.
- Открытие капсул не зависит от посещения сайта.
- Не требуется отдельный постоянно работающий сервер для фоновых задач.

**Недостатки:**

- Архитектура становится сложнее.
- Необходимо настраивать IAM-роли и сетевой доступ.
- Требуется контролировать состояние очередей и журналов.
- Возможны повторные доставки сообщений.
- Открытие капсулы может происходить с небольшой задержкой из-за расписания.
- Использование дополнительных сервисов AWS может создавать дополнительные расходы.

## Сравнение вариантов

| Критерий | Веб-запрос | Cron | AWS Lambda |
|---|---|---|---|
| Независимость от посещения сайта | Нет | Да | Да |
| Влияние фоновых задач на время ответа | Высокое | Низкое | Низкое |
| Автоматические повторные попытки | Нет | Требуется реализация | Да, через SQS |
| Хранение необработанных сообщений | Нет | Требуется реализация | SQS и DLQ |
| Отдельный работающий сервер для фоновых задач | Нет | Требуется работающий EC2 | Нет |
| Сложность настройки | Низкая | Средняя | Выше |
| Масштабируемость | Ограниченная | Требует дополнительных решений | Высокая |

## Решение

Было принято решение использовать третий вариант — AWS Lambda совместно с Amazon SNS, Amazon SQS и EventBridge Scheduler.

В приложении используются следующие ресурсы:

- `timecapsule-dev-events` — тема Amazon SNS для распространения событий.
- `timecapsule-dev-mail` — основная очередь сообщений.
- `timecapsule-dev-mail-dlq` — очередь необработанных сообщений.
- `timecapsule-dev-mailer` — Lambda-функция создания уведомлений.
- `timecapsule-dev-opener` — Lambda-функция автоматического открытия капсул.
- `timecapsule-dev-open-capsules` — расписание EventBridge Scheduler.

### Запечатывание капсулы

После запечатывания капсулы PHP-приложение публикует событие `capsule.sealed` в SNS.

SNS передаёт сообщение в SQS. Служба Lambda получает сообщение из очереди и вызывает Lambda Mailer, которая подключается к PostgreSQL и создаёт запись в таблице `notifications`.

Таким образом, создание уведомления выполняется отдельно от веб-запроса.

### Открытие капсулы

EventBridge Scheduler каждую минуту запускает Lambda Opener.

Функция проверяет время открытия капсул, обновляет их состояние и создаёт соответствующие уведомления в базе данных.

После успешного асинхронного выполнения служба Lambda отправляет запись о вызове в SNS через настроенное назначение (Destination).

Подписка SNS фильтрует сообщения таким образом, чтобы электронные письма приходили только тогда, когда была открыта хотя бы одна капсула.

Старый механизм открытия капсул внутри PHP-приложения был удалён.

## Последствия

### Уменьшение времени ответа

После переноса создания уведомлений в Lambda время выполнения запроса Seal capsule уменьшилось приблизительно с 3,22 секунды до 0,368 секунды.

Пользователь больше не ожидает завершения создания уведомления.

### Сбой Lambda Mailer

Если Lambda Mailer завершается с ошибкой, сообщение не удаляется из основной очереди.

После завершения Visibility timeout сообщение снова становится доступным для обработки.

В рабочей конфигурации используются следующие параметры:

- Visibility timeout — 180 секунд.
- Maximum receives — 5.
- Message retention period — 4 дня.

После исчерпания допустимого количества получений сообщение перемещается в Dead-letter queue.

После устранения причины ошибки сообщения можно вернуть в основную очередь с помощью DLQ Redrive.

### Остановка базы данных

Если база данных RDS остановлена, Lambda Mailer не сможет создать уведомление.

Сообщения останутся в SQS и будут повторно обрабатываться. Если база данных не станет доступной до исчерпания допустимого количества попыток, сообщения переместятся в DLQ.

После запуска базы данных сообщения можно повторно обработать.

Lambda Opener также не сможет открыть капсулы при недоступной базе данных. После восстановления подключения очередной успешный запуск функции обработает капсулы, время открытия которых уже наступило.

### Защита от повторных сообщений

Amazon SQS Standard допускает повторную доставку одного сообщения.

Для предотвращения дублирования уведомлений используется уникальное ограничение по полям `capsule_id` и `event_type`.

При добавлении уведомления используется SQL-конструкция:

```sql
ON CONFLICT (capsule_id, event_type) DO NOTHING
```

Если уведомление для данной капсулы и данного типа события уже существует, повторная запись не создаётся.

Lambda Opener дополнительно проверяет условие:

```sql
WHERE opened_at IS NULL
```

Благодаря этому уже открытые капсулы не обрабатываются повторно.

### Ограничения решения

Использование SNS и SQS повышает надёжность обработки, но не гарантирует отсутствие потерь во всех ситуациях.

Например, если капсула успешно запечатана в базе данных, но публикация события в SNS завершилась ошибкой, сообщение может не попасть в очередь.

Аналогично, если Lambda Opener успешно обновила базу данных, но служба Lambda не смогла доставить запись о вызове в SNS, капсула останется открытой, однако электронное письмо может не прийти.

Такие ситуации требуют дополнительных механизмов контроля и восстановления.

## Проверка принятого решения

В ходе лабораторной работы был проведён эксперимент с искусственным сбоем Lambda Mailer.

Для этого в настройках функции временно указали неправильный пароль базы данных и запечатали две тестовые капсулы.

Для ускорения эксперимента Maximum receives временно уменьшили с 5 до 2.

В результате:

1. Lambda Mailer завершалась с ошибкой подключения к PostgreSQL.
2. SQS повторно передавала сообщения на обработку.
3. Оба сообщения переместились в DLQ.
4. Правильный пароль базы данных был восстановлен.
5. Сообщения были возвращены в основную очередь через DLQ Redrive.
6. Lambda Mailer успешно создала уведомления для обеих капсул.
7. Для каждой тестовой капсулы было создано ровно одно уведомление.
8. Исходное значение Maximum receives было восстановлено.

Также было проверено автоматическое открытие капсул без посещения сайта.

Полученные результаты подтвердили работоспособность выбранной архитектуры.

## Заключение

Использование AWS Lambda, Amazon SNS и Amazon SQS позволило отделить фоновые задачи от основной логики PHP-приложения.

Приложение стало быстрее отвечать на запросы пользователей, получило механизм повторной обработки сообщений и возможность автоматического открытия капсул независимо от посещения сайта.

Несмотря на увеличение сложности архитектуры, выбранное решение обеспечивает более высокую отказоустойчивость, масштабируемость и удобство обслуживания приложения TimeCapsule.
