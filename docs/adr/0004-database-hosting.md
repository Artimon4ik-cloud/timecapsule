# ADR-0004: Размещение базы данных — миграция с EC2 на Amazon RDS

**Статус:** Принято  
**Дата:** 05.11.2026  
**Проект:** TimeCapsule

## 1. Контекст

Изначально в проекте TimeCapsule использовалась база данных PostgreSQL, установленная на отдельном экземпляре Amazon EC2 в приватной подсети VPC.

Такой подход требовал самостоятельного администрирования сервера: установки обновлений, настройки резервного копирования, мониторинга, обеспечения безопасности и восстановления базы данных при сбоях.

Для упрощения инфраструктуры было принято решение перейти на управляемый сервис баз данных Amazon RDS.

Основные цели миграции:

- Сократить объём ручного администрирования PostgreSQL.
- Использовать автоматическое резервное копирование.
- Обеспечить безопасное подключение к базе данных внутри VPC.
- Упростить обслуживание и восстановление базы.
- Сохранить работоспособность существующего приложения TimeCapsule.

## 2. Рассмотренные альтернативы

| Решение | Преимущества | Недостатки |
|---|---|---|
| PostgreSQL на EC2 | Полный контроль над сервером и конфигурацией PostgreSQL | Необходимость самостоятельно выполнять обновления, резервное копирование и восстановление |
| Amazon RDS Single-AZ | Управляемая база данных, автоматические резервные копии, простое администрирование | Отсутствие автоматического переключения на другую зону доступности |
| Amazon RDS Multi-AZ | Повышенная доступность, автоматическое переключение при сбое | Более высокая стоимость |
| Amazon Aurora PostgreSQL | Высокая масштабируемость, управляемая инфраструктура, дополнительные возможности отказоустойчивости | Более высокая сложность и потенциально большие расходы |

## 3. Принятое решение

Для проекта TimeCapsule выбран **Amazon RDS for PostgreSQL в конфигурации Single-AZ**.

Основные параметры:

| Параметр | Значение |
|---|---|
| Идентификатор RDS | `lab5-db` |
| СУБД | PostgreSQL 18.3 |
| Тип экземпляра | `db.t4g.micro` |
| Хранилище | 20 GiB, gp3 |
| Размещение | Single-AZ |
| VPC | `timecapsule-dev-vpc` |
| Публичный доступ | Отключён |
| База приложения | `timecapsule_db` |
| Пользователь приложения | `timecapsule_user` |
| Автоматические резервные копии | Включены, хранение 1 день |
| Шифрование хранилища | Включено |
| Подключение | PostgreSQL, TCP 5432, SSL/TLS |

База данных размещена в приватной подсети. DB Subnet Group включает приватные подсети двух зон доступности.

Для подключения приложения используется приватная DNS-запись Amazon Route 53:

`db.timecapsule.internal`

Эта запись типа CNAME указывает на endpoint Amazon RDS.

Благодаря этому приложение не зависит от непосредственного указания адреса RDS в конфигурации: при изменении сервера достаточно обновить DNS-запись.

Дополнительно настроен Amazon EventBridge Scheduler для автоматической остановки RDS ежедневно в 23:00 по часовому поясу `Europe/Chisinau`.

Для выполнения операции используется IAM-роль `timecapsule-dev-scheduler-role` с разрешением `rds:StopDBInstance` для конкретного экземпляра базы данных.

## 4. Последствия решения

### Преимущества

1. **Упрощение администрирования.** Amazon RDS берёт на себя часть задач по обслуживанию инфраструктуры PostgreSQL.

2. **Резервное копирование.** Используются автоматические резервные копии и возможность восстановления базы данных.

3. **Повышение безопасности.** База данных не имеет публичного доступа. Подключение разрешено через Security Group сервера приложения.

4. **Шифрование.** Используется шифрование хранилища и SSL/TLS для соединения с PostgreSQL.

5. **Удобство изменения инфраструктуры.** Route 53 позволяет изменить конечный адрес базы данных без изменения программного кода приложения.

6. **Оптимизация расходов.** EventBridge Scheduler позволяет останавливать базу в периоды, когда она не используется.

### Недостатки и риски

1. Конфигурация Single-AZ не обеспечивает автоматическое переключение на другую зону доступности при отказе основной зоны.

2. Во время перезагрузки или остановки RDS приложение временно теряет доступ к базе данных.

3. Запланированная остановка RDS делает функции приложения, зависящие от PostgreSQL, недоступными до повторного запуска базы.

4. Временно остановленный экземпляр Amazon RDS автоматически запускается не позднее чем через 7 дней.

5. При остановленном RDS могут продолжать начисляться расходы за хранилище и резервные копии.

6. Используемый AWS Free Plan ограничивает срок хранения автоматических резервных копий одним днём.

## 5. Резервное копирование и восстановление

В Amazon RDS включено автоматическое резервное копирование с периодом хранения **1 день**.

Была предпринята попытка увеличить период хранения до 7 дней, однако AWS отклонил изменение из-за ограничений Free Plan.

Возможность восстановления на определённый момент времени зависит от доступных резервных копий и последнего времени восстановления (Latest restorable time).

**RPO (Recovery Point Objective)** — максимально допустимая потеря данных при сбое.

**RTO (Recovery Time Objective)** — максимально допустимое время восстановления работоспособности.

В данной лабораторной конкретные значения RPO и RTO не гарантируются, поскольку зависят от характера сбоя и выбранного способа восстановления.

Для более высокой доступности в промышленной среде рекомендуется рассмотреть Amazon RDS Multi-AZ.

## 6. Проверка принятого решения

После миграции были выполнены следующие проверки:

1. Создана резервная копия PostgreSQL со старого EC2-сервера с использованием `pg_dump`.

2. Данные восстановлены в Amazon RDS с помощью `pg_restore`.

3. Проверены таблицы и количество записей в перенесённой базе данных.

4. Настроено подключение приложения через приватную DNS-запись Route 53.

5. Проверено создание новых записей через веб-интерфейс TimeCapsule.

6. Старый EC2-сервер PostgreSQL остановлен. После этого приложение продолжило работать с Amazon RDS.

7. Выполнена перезагрузка RDS. Во время перезагрузки приложение показало ошибку подключения к базе данных (HTTP 500).

8. После завершения перезагрузки RDS приложение автоматически восстановило работоспособность.

9. Выполнена временная остановка RDS. Подтверждена недоступность базы данных для приложения.

10. После повторного запуска RDS сайт TimeCapsule снова начал работать.

11. В журналах RDS обнаружены события остановки и перезагрузки.

12. В AWS CloudTrail подтверждена регистрация административных операций `RebootDBInstance` и `StopDBInstance`.

Расписание EventBridge Scheduler настроено, однако отдельное тестирование его автоматического выполнения не проводилось.

## 7. Итоговое решение

Для TimeCapsule выбран Amazon RDS PostgreSQL Single-AZ как оптимальный для текущего учебного проекта вариант по соотношению функциональности, сложности обслуживания и стоимости.

Миграция PostgreSQL с EC2 на Amazon RDS выполнена успешно.

Приложение TimeCapsule использует Amazon RDS в качестве основной базы данных, подключается к ней через приватную DNS-запись Route 53 и поддерживает восстановление подключения после перезапуска базы.

В дальнейшем при необходимости повышения отказоустойчивости архитектура может быть расширена до Amazon RDS Multi-AZ.
