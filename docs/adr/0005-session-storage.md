# ADR-0005: Хранение пользовательских сессий в Amazon DynamoDB
 
## 1. Контекст

Приложение TimeCapsule развёрнуто в AWS с использованием Application Load Balancer (ALB) и Auto Scaling Group (ASG).

Auto Scaling Group управляет несколькими EC2-инстансами, автоматически увеличивая или уменьшая их количество в зависимости от нагрузки.

Возникает проблема: если PHP-сессии хранятся локально на EC2, пользователь может потерять авторизацию при переключении на другой сервер.

Поэтому необходимо организовать централизованное хранилище сессий, доступное всем EC2-инстансам.

## 2. Рассмотренные варианты

### Вариант 1. Sticky Sessions (ALB)

ALB направляет запросы одного пользователя на один и тот же EC2-инстанс.

**Преимущества:**
- Простая настройка.
- Не требуется отдельная база данных для сессий.

**Недостатки:**
- При остановке EC2 локальная сессия может быть потеряна.
- Привязка пользователя к серверу ограничивает гибкость распределения нагрузки.

### Вариант 2. Amazon RDS (PostgreSQL)

Пользовательские сессии сохраняются в общей базе данных PostgreSQL.

**Преимущества:**
- Централизованное хранение.
- Использование существующей базы данных.

**Недостатки:**
- Дополнительная нагрузка на основную базу.
- Необходимость реализации хранения и очистки сессий.
- Зависимость работы сессий от доступности RDS.

### Вариант 3. Amazon DynamoDB

PHP-сессии сохраняются в отдельной таблице DynamoDB, доступной всем EC2-инстансам.

**Преимущества:**
- Централизованное хранение сессий.
- Автоматическое масштабирование сервиса.
- TTL для автоматического удаления устаревших записей.
- Не требуется управлять отдельным сервером базы данных.
- Поддержка разграничения доступа через IAM.

**Недостатки:**
- Дополнительные расходы на запросы и хранение.
- Зависимость от AWS DynamoDB.
- Необходимость интеграции с AWS SDK.

## 3. Принятое решение

Для хранения пользовательских сессий TimeCapsule выбрана **Amazon DynamoDB**.

Создана таблица `timecapsule-dev-sessions` со следующими параметрами:

- Partition Key: `id` (String).
- Режим оплаты: On-demand.
- TTL attribute: `expires`.

Для доступа к таблице используется IAM Role `timecapsule-dev-ec2-s3-role` с отдельной политикой `timecapsule-dev-app-sessions`.

Политика разрешает только необходимые операции: `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`.

В PHP-приложении используется AWS SDK for PHP и обработчик `Aws\DynamoDb\SessionHandler`.

## 4. Последствия решения

Положительные последствия:

- Авторизация не зависит от конкретного EC2-инстанса.
- ALB может направлять запросы на разные серверы.
- Auto Scaling Group может создавать и удалять EC2 без потери централизованно сохранённых сессий.
- Истёкшие сессии удаляются через TTL.

Ограничения:

- Приложению необходим доступ к DynamoDB.
- Возникают дополнительные расходы на использование сервиса.
- Для безопасной работы требуется корректная IAM-политика.

## 5. Проверка решения

В ходе лабораторной работы:

1. Настроена таблица DynamoDB для хранения PHP-сессий.
2. Выполнен вход пользователя в TimeCapsule.
3. Подтверждено появление записи сессии в DynamoDB.
4. Проверено сохранение авторизации при повторных запросах через ALB.
5. Проведено нагрузочное тестирование: Auto Scaling увеличил количество EC2 с 2 до 4.
6. После снижения нагрузки количество EC2 автоматически уменьшилось с 4 до 2.
7. Повторно проверена работа сайта и сохранение авторизации.

**Результат:** выбранное решение обеспечивает централизованное хранение пользовательских сессий и поддерживает горизонтальное масштабирование приложения.
