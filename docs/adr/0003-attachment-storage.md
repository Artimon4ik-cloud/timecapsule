# ADR-0003: Хранение пользовательских вложений в Amazon S3

**Статус:** Принято  
**Проект:** TimeCapsule  
**Регион AWS:** eu-central-1 (Frankfurt)

## Контекст

Приложение TimeCapsule позволяет пользователям создавать капсулы времени и прикреплять к ним изображения.

Ранее файлы хранились локально на диске EC2 app-server. Такой подход создаёт проблемы при замене сервера, потере данных и горизонтальном масштабировании приложения.

Необходимо выбрать надёжное и безопасное хранилище пользовательских вложений, которое не зависит от жизненного цикла EC2.

## Рассмотренные варианты

### 1. Amazon EBS

Хранение файлов на диске, подключённом к EC2.

**Преимущества:**
- Простая интеграция с PHP-приложением.
- Быстрый доступ к файлам с сервера.

**Недостатки:**
- Хранилище привязано к конкретной зоне доступности.
- Для нескольких серверов требуется дополнительная организация доступа к файлам.
- Необходимо самостоятельно управлять резервным копированием.

### 2. Amazon EFS

Общая файловая система, доступная нескольким EC2.

**Преимущества:**
- Несколько серверов могут использовать одни файлы.
- Не требуется переносить вложения между серверами.

**Недостатки:**
- Дополнительные расходы на файловую систему.
- Требуется настройка сетевого доступа и монтирования.
- Для хранения изображений через веб-приложение возможности общей файловой системы избыточны.

### 3. Amazon S3

Объектное хранилище AWS для пользовательских вложений.

**Преимущества:**
- Файлы не зависят от конкретного EC2.
- Высокая надёжность хранения.
- Удобное масштабирование.
- Поддержка Versioning, Lifecycle Rules и шифрования.
- Возможность предоставлять временный доступ через Presigned URL.

**Недостатки:**
- Для работы требуется интеграция с AWS SDK.
- Оплачиваются хранение, запросы и применимая передача данных.
- S3 не является обычной файловой системой.

## Решение

Выбрано **Amazon S3**.

Для проекта создан приватный бакет:

`timecapsule-dev-uploads-artimon4ik`

Целевая структура хранения вложений:

`uploads/`

PHP-приложение использует AWS SDK for PHP и IAM Role:

`timecapsule-dev-ec2-s3-role`

Для доступа к S3 не используются статические AWS Access Keys.

Основные операции:
- `PutObject` — загрузка вложений.
- `DeleteObject` — удаление вложений.
- `GetObject` через Presigned URL — получение файлов пользователем.

## Последствия

### Получение файлов пользователем

При запросе вложения PHP-приложение создаёт временную подписанную ссылку S3.

Браузер переходит по этой ссылке и скачивает файл напрямую из S3, без передачи содержимого через EC2.

Срок действия ссылки — **5 минут**. После истечения этого времени требуется получить новую ссылку. Фактический доступ также зависит от действительности учётных данных, использованных при подписании, и действующих разрешений.

### Защита от удаления и контроль стоимости

В бакете включено **Versioning**, позволяющее сохранять предыдущие версии объектов и восстанавливать данные после случайного удаления или перезаписи.

Настроено **Lifecycle Rule** для удаления неактуальных версий через 30 дней, что ограничивает накопление старых версий и расходы на хранение.

Бакет закрыт от публичного доступа с помощью **Block Public Access**, а объекты шифруются с использованием **SSE-S3**.

### Масштабирование приложения

При появлении нескольких EC2 app-server за Application Load Balancer все экземпляры приложения смогут обращаться к одному S3-бакету.

Не потребуется синхронизировать пользовательские вложения между серверами или использовать общий локальный диск.

Каждый сервер сможет получать доступ к S3 через назначенную ему IAM Role с необходимыми разрешениями.

## Итог

Amazon S3 выбран как наиболее подходящее хранилище пользовательских вложений TimeCapsule благодаря независимости от EC2, возможностям масштабирования, контролю доступа и механизмам защиты данных.
